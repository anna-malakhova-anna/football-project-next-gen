# Counting Flag Football

A governed participation data platform for a **synthetic** global flag football program: messy partner data in,
a clean common schema, data-quality profiling and governance artifacts out. Built with Python (data generation
and loading only), DuckDB and dbt. The SQL is the showcase.

> ## All data in this project is synthetic
> Every person, email, phone number and record is fake, generated by `generator/` from a fixed random seed.
> The real equivalent of this data is **minors' personal information** (children aged 5 to 17, their guardians'
> contact details, photo and marketing consent). That is exactly why this project uses invented people: the
> modelling, privacy and governance patterns can be built and shown in public without exposing a real child.
> Email addresses use reserved example domains and phone numbers use the fictional 555-01xx range.

## What Phase 1 does

```
 generator/ (seed 42)                          dbt (all cleaning is SQL)
 ┌──────────────────────┐   raw files    ┌──────────┐  ┌─────────┐  ┌──────────────┐  ┌─────────┐
 │ true-person registry │ ─────────────▶ │   raw    │─▶│ staging │─▶│ intermediate │─▶│ quality │
 │ + 3 source exports   │  CSV / JSON /  │ (strings │  │ 1 per   │  │ unioned      │  │ profile │
 └──────────┬───────────┘  XLSX          │  as-is)  │  │ source  │  │ common schema│  │ defects │
            │                            └──────────┘  └─────────┘  └──────────────┘  │ summary │
            ▼                             loader/load_raw.py                          └─────────┘
 data/ground_truth/  (quarantined: never loaded, never referenced by dbt)
```

| Source | Format | Rows | The mess |
|---|---|---|---|
| `US_LEAGUE` | CSV per season | 10,566 | mixed date and label formats, double submits, near-duplicates, dropped ZIP zeros, blank consents |
| `CA_CLUB` | paginated JSON | 1,988 | nested records, birth year only, bilingual programs, accents and caps, missing consent objects, page-overlap duplicates |
| `INTL_FED` | XLSX, one sheet per country | 1,686 | title rows, summary rows, Excel date serials, inconsistent country names, family-name-first sheet, reissued IDs |

The generator first builds a registry of 6,000 true people (households with siblings, churn by age, cross-border
movers, a growing share of girls, multi-league play), then derives each source from it and injects every defect at an
exact configured rate (`config/generation.yaml`). The registry and a map from every source record to its true person
are written to `data/ground_truth/` so that Phase 2 can measure identity resolution against the truth.

## Run it

Requires [`uv`](https://docs.astral.sh/uv/) and `make`. Python 3.11 to 3.13 is fetched automatically.

```bash
make setup      # install dependencies, create dbt/profiles.yml from the example
make all        # generate -> load -> build -> test   (about 30 seconds)
```

| Command | What it does |
|---|---|
| `make generate` | writes `data/raw/` and `data/ground_truth/`, and exports configured defect rates to a dbt seed |
| `make load` | lands the files in DuckDB schema `raw` with no transformation |
| `make build` | `dbt seed` and `dbt run` |
| `make test` | `pytest` (generator, loader, seeds, docs) and `dbt test` |
| `make docs` | regenerates `docs/data_dictionary.md` from the dbt YAML |
| `make clean` | removes generated data, the warehouse and dbt artifacts |

Explore the result in `warehouse/flag.duckdb`, for example:

```sql
select * from quality.dq_summary;                       -- observed vs configured defect rates
select * from quality.dq_source_profile;                -- per source x column profile
select * from intermediate.int_registrations_unioned;   -- the common schema
```

## Design principles

1. **SQL is the showcase.** Python generates and loads; cleaning, typing and profiling are dbt SQL.
2. **Raw is immutable.** Strings in, strings stored (empty CSV fields stay `''`, Excel serials stay raw text).
3. **Deterministic.** One seed (42). Two independent clones produce byte-identical files, parquet and xlsx included.
4. **Messiness is specified.** Defects are injected at exact counts from the config, so detection can be checked.
5. **Ground truth is quarantined.** It never enters `raw` or any dbt model; tests enforce this.
6. **Never guess.** Ambiguous dates, unmapped values and unparseable fields become NULL or `U` and are flagged.
   Consent that was not captured is `NULL`, never `FALSE`.

## Phase 1 status: complete

| Definition of done | Result |
|---|---|
| `make all` runs clean from an empty clone in under 2 minutes | about 30 s including `uv sync` (checked on a fresh copy) |
| Generator is deterministic | identical hashes across two independent clones, and in tests |
| Ground truth never in the DuckDB `raw` schema | pytest and a dbt singular test |
| All three sources land in raw with zero transformation | row counts match the files; everything is `VARCHAR` apart from lineage columns |
| All models build and all tests pass; warn only on `country_code` | 52 pytest, 51 dbt tests, 0 warnings (the `country_code` warn test has nothing to flag) |
| `dq_summary` shows observed vs configured for every injected defect | 34 detectable checks pass (rates within tolerance, structural counts exact, never-injected flags at 0); **8 defects are listed as `NOT_DETECTABLE_PHASE1`** (see below) |
| Every raw division / program / category label maps to a canonical division | singular test fails the build otherwise |
| Consent NULL is never coerced to FALSE | singular test |
| Source inventory, data dictionary, user stories, both ADRs | in `docs/` |
| README states the data is synthetic and why | above |

**What "not detectable" means.** Eight injected defects cannot be seen in staged data alone: US name typos,
nickname use, changed guardian emails and swapped day/month DOBs; CA accent stripping and off-by-one birth years;
Japan's name order (a sheet rule) and Panama's reissued IDs. They appear in `dq_summary` with their configured rate
and no observed value. Reading the ground truth to fill them in would break the quarantine rule, so they are the
evaluation targets for Phase 2.

**Where the build adds to the spec** (all documented in code or docs):
- extra config keys: `missing_marketing_opt_in`, `zip_leading_zero_dropped`, `null_photo_media`,
  `null_casl_marketing`, `missing_media_consent`, intl email presence rates;
- the registration key includes an occurrence number, because exact duplicates repeat their source id;
- `defect_manifest.parquet` (ground truth) lists every injected defect by record, for Phase 2 evaluation;
- division boundaries do not line up exactly across sources (CA `Atome` and intl `U15` notes in `division_map`).

## Roadmap

| Phase | Theme | Key outputs |
|---|---|---|
| **1 Foundations** (done) | Sources, ingestion, staging, DQ | 3 synthetic sources + hidden ground truth, DuckDB raw layer, dbt staging + unioned model, DQ profile, source inventory, data dictionary v1 |
| 2 Identity | Who is the same person? | Blocking + fuzzy match in SQL, match-confidence tiers, `dim_participant` with survivorship rules, precision/recall against ground truth |
| 3 Measurement and privacy | What counts as a participant? | Unique participants vs registrations, methodology memo, consent-aware and minor-masked views, role-based access pattern |
| 4 Outcomes and scale | Does playing create fans? | Retention cohorts, participant to fan funnel, 2 more sources (fan engagement, school counts), source-onboarding playbook, polish |
