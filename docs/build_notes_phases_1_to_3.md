# Flag Football Project

A governed participation data platform for a **synthetic** global flag football program: messy partner data in,
a clean common schema, data-quality profiling and governance artifacts out. Built with Python (data generation
and loading only), DuckDB and dbt. The SQL is the showcase.

> ## All data in this project is synthetic
> Every person, email, phone number and record is fake, generated by `generator/` from a fixed random seed.
> The real equivalent of this data is **minors' personal information** (children aged 5 to 17, their guardians'
> contact details, photo and marketing consent). That is exactly why this project uses invented people: the
> modelling, privacy and governance patterns can be built and shown in public without exposing a real child.
> Email addresses use reserved example domains and phone numbers use the fictional 555-01xx range.

## What Phase 1 does

```

 ┌──────────────────────┐   raw files    ┌──────────┐  ┌─────────┐  ┌──────────────┐  ┌─────────┐
 │ true-person registry │ ─────────────▶ │   raw    │─▶│ staging │─▶│ intermediate │─▶│ quality │
 │ + 3 source exports   │  CSV / JSON /  │ (strings │  │ 1 per   │  │ unioned      │  │ profile │
 └──────────┬───────────┘  XLSX          │  as-is)  │  │ source  │  │ common schema│  │ defects │
            │                            └──────────┘  └─────────┘  └──────────────┘  │ summary │
            ▼                             loader/load_raw.py                          └─────────┘
 data/ground_truth/  (quarantined: never loaded, never referenced by dbt)
```

| Source | Format | Rows | The mess |
|---|---|---|---|
| `US_LEAGUE` | CSV per season | 12,929 | mixed date and label formats, double submits, near-duplicates, dropped ZIP zeros, blank consents |
| `CA_CLUB` | paginated JSON | 2,522 | nested records, birth year only, bilingual programs, accents and caps, missing consent objects, page-overlap duplicates |
| `INTL_FED` | XLSX, one sheet per country | 2,079 | title rows, summary rows, Excel date serials, inconsistent country names, family-name-first sheet, reissued IDs |

The generator first builds a registry of 6,000 true people observed over **five years (2021 to 2025)**; the first, 2021, is left-censored (set in config, `seasons.first_observed_year`) (households with siblings, churn by age, cross-border
movers, a growing share of girls, multi-league play), then derives each source from it and injects every defect at an
exact configured rate (`config/generation.yaml`). The registry and a map from every source record to its true person
are written to `data/ground_truth/` so that Phase 2 can measure identity resolution against the truth.

## Run it

Requires [`uv`](https://docs.astral.sh/uv/) and `make`. Python 3.11 to 3.13 is fetched automatically.

```bash
make setup      # install dependencies, create dbt/profiles.yml from the example
make all        # Phase 1: generate -> load -> build -> test   (about 30 seconds)
make phase2     # Phase 1 + identity resolution + evaluation       (about 55 seconds)
```

| Command | What it does |
|---|---|
| `make generate` | writes `data/raw/` and `data/ground_truth/`, and exports configured defect rates to a dbt seed |
| `make load` | lands the files in DuckDB schema `raw` with no transformation |
| `make build` | `dbt seed` and `dbt run` |
| `make test` | `pytest` (generator, loader, seeds, docs) and `dbt test` |
| `make load-eval` | loads the quarantined ground truth into schema `eval` (Phase 2; separate from `make load`) |
| `make idr` | identity resolution and marts: `dbt run --select identity marts` |
| `make eval` | evaluation models, headline table, and CSV exports to `docs/eval/` |
| `make phase2` | everything: all, load-eval, idr, eval, every dbt test, the isolation check and an ID-stability check |
| `make steward-demo` / `make steward-reset` | optional demo of the review loop with a **simulated** steward (see below) |
| `make measure` / `make shares` / `make report` / `make publish YEAR=2025` / `make phase3` | Phase 3: counting facts and marts, audience shares and the policy check, the executive report, immutable snapshots (see the Phase 3 section) |
| `make docs` | regenerates the data dictionary, `docs/metrics.md` and `docs/access_policy.md` from their sources |
| `make clean` | removes generated data, the warehouse and dbt artifacts |

Explore the result in `warehouse/flag.duckdb`, for example:

```sql
select * from quality.dq_summary;                       -- observed vs configured defect rates
select * from quality.dq_source_profile;                -- per source x column profile
select * from intermediate.int_registrations_unioned;   -- the common schema
```

## Design principles

1. **SQL is the showcase.** Python generates and loads; cleaning, typing and profiling are dbt SQL.
2. **Raw is immutable.** Strings in, strings stored (empty CSV fields stay `''`, Excel serials stay raw text).
3. **Deterministic.** One seed (42). Two independent clones produce byte-identical files, parquet and xlsx included.
4. **Messiness is specified.** Defects are injected at exact counts from the config, so detection can be checked.
5. **Ground truth is quarantined.** It never enters `raw` or any dbt model; tests enforce this.
6. **Never guess.** Ambiguous dates, unmapped values and unparseable fields become NULL or `U` and are flagged.
   Consent that was not captured is `NULL`, never `FALSE`.

**What "not detectable" means.** Nine injected defects cannot be seen in staged data alone: US name typos,
nickname use, changed guardian emails and swapped day/month DOBs; CA accent stripping and off-by-one birth years;
Japan's name order (a sheet rule), Panama's reissued IDs, and (added in Phase 2) a changed family name. They appear in `dq_summary` with their configured rate
and no observed value. Reading the ground truth to fill them in would break the quarantine rule, so they are the
evaluation targets for Phase 2.

**Where the build adds to the spec** (all documented in code or docs):
- extra config keys: `missing_marketing_opt_in`, `zip_leading_zero_dropped`, `null_photo_media`,
  `null_casl_marketing`, `missing_media_consent`, intl email presence rates;
- the registration key includes an occurrence number, because exact duplicates repeat their source id;
- `defect_manifest.parquet` (ground truth) lists every injected defect by record, for Phase 2 evaluation;
- division boundaries do not line up exactly across sources (CA `Atome` and intl `U15` notes in `division_map`).

## Phase 2: identity resolution (who is the same person?)

Turns 17,530 registrations into 6,000 participants (the generator's true population is also 6,000) **in SQL only**, without the
matcher ever seeing the answer key, then measures how well that worked. Ground truth lives in a separate `eval` schema and
is read only by `models/evaluation/`; `scripts/check_eval_isolation.py` fails the build if anything else depends on it.
Business explainer: [docs/identity_resolution.md](identity_resolution.md). Decisions:
[ADR-003](decisions/ADR-003-identity-resolution.md), [ADR-004](decisions/ADR-004-participant-id-stability.md).
Generated results: [docs/phase2_results.md](phase2_results.md).

**Why it matters.** Every participation number in Phase 3 depends on it. *Under-merging* (one child split in two) inflates
participation and breaks retention. *Over-merging* (two children collapsed) undercounts, and can apply one child's consent
to a sibling, which is a privacy incident. So the project **biases toward precision**.

Pipeline: exact duplicates collapsed, then deterministic links (shared source IDs), blocking (five blocks, pair
completeness 0.9998, 66,826 candidate pairs), agreement-level features, two matchers (a rules baseline and a
Fellegi-Sunter probabilistic matcher with explainable weights and hard guardrails), connected-components clusters in a
recursive CTE (macro `connected_components`), cluster-integrity checks, a prioritised review queue, and three marts
(`bridge_registration_participant`, `dim_participant`, `participant_identifiers`).

**Headline results** (automatic merges only, before any steward review; 755 of the 6,000 people have a sibling in the data;
five-year window):

| Matcher | Scope | Precision | Recall | F1 | Sibling/twin merges | Predicted vs true participants |
|---|---|---|---|---|---|---|
| Rules baseline | AUTO | 0.9994 | 0.9228 | 0.9595 | 2 | 6,513 vs 6,000 |
| Fellegi-Sunter, spec-literal (`fs_naive`) | AUTO | 0.9635 | 0.9999 | 0.9814 | **86** | 5,906 vs 6,000 |
| **Fellegi-Sunter, final (`fs`)** | **AUTO** | **0.9991** | **0.9996** | **0.9994** | **2** | **6,000 vs 6,000** |
| Fellegi-Sunter, final (`fs`) | AUTO + PROBABLE | 0.9947 | 0.9998 | 0.9972 | 5 | 5,983 vs 6,000 |

> **The steward in this project is simulated.** `scripts/simulate_steward.py` resolves review-queue items using the
> ground truth, only to demonstrate the feedback loop (`make steward-demo`). Its results appear as separate `POST_REVIEW`
> rows and **must never be quoted as matcher performance**. The committed `review_decisions` seed is empty.

**Honest notes**
- The spec-literal matcher merged siblings and twins (86 clusters) because email, phone and postal code are one household
  counted three times. The final `fs` fixes the model structure (count positive household evidence once, a household
  guard, a cap on DOB disagreement). Those fixes were prompted by the evaluation, not by tuning m-values, and are
  disclosed in ADR-003 with the step-by-step metrics. The thresholds (0.997 / 0.85) were chosen once from the sweep on the
  original three-year data and re-read, not re-tuned, since.
- **Extending the window to five years exposed a limit.** On three years `fs` had no sibling/twin false merges at AUTO; on five it
  has 2 clusters (0.27% of the 755 multi-child households), and the rules baseline has the same 2. Both are Canadian siblings
  with the same first and last name born in the same year in one household; Canada gives only a birth year, so no feature
  separates them. Nothing was tuned to hide it. It misses the 0.1% target at AUTO (and at AUTO + PROBABLE, 5 clusters, 0.66%).
- The final matcher wins on recall (0.9996 vs 0.923) and on counting people (6,000 vs 6,513), and no longer ties the baseline on
  sibling/twin merges: it ties it at 2 each at AUTO.
- 5 true pairs are lost to the household guard, 3 more fall below the threshold, and 2 belong to name-change cases; 16 false sibling
  pairs and 6 transitive-chain pairs come from the two clusters above, plus 4 look-alike pairs (same first name, near-identical
  surname, same birth year, no contact data).
- 55 of the 100 cross-border movers also register in both countries in the year they move, so some people appear in two
  countries in one year (this matters for the Phase 3 country counts).
- The synthetic data flatters the matcher (phone numbers never change; the nickname map covers every generated nickname).

## Phase 3: measurement and privacy (how many people play, and how sure are we?)

Turns resolved participants into numbers an executive can trust and data each audience is allowed to see. **All data is synthetic.**
A count is **registered participants in onboarded sources**: not total participation, and a registration is not proof that
someone played.

- **A defined, versioned methodology** (v1.0): counting rules C1 to C15, in [ADR-005](decisions/ADR-005-counting-rules.md) and the
  [methodology memo](methodology/counting-a-participant.md). **The memo is a draft skeleton: every heading, rule and number is in
  place, and the prose is Anna's to write.**
- **One counting engine** (`fct_registration` -> `fct_participant_year`, plus a US-season fact) behind every mart, share and report. Global
  unique participants are **not** the sum of country presence counts; both views exist and are labelled, and tests prove the arithmetic.
- **Honest uncertainty:** a low / point / high identity range computed without ground truth (the same `connected_components` macro over three
  edge sets), reported beside the headline numbers, with a separately labelled comparison against the synthetic truth.
- **Audience shares with privacy controls** enforced by tests: exec (aggregates, small cells suppressed), analyst (pseudonymous participant-year),
  ops (full identifiers), marketing (consented contacts only), media (cleared roster only). [access_policy.md](access_policy.md),
  [ADR-006](decisions/ADR-006-privacy-controls.md).
- **A KPI scorecard**, **publish and restatement** (immutable snapshots; a log that names the likely cause of any change;
  [ADR-007](decisions/ADR-007-publish-and-restatement.md)) and an **executive report** rendered with no calculations
  ([2025 report](reports/participation_report_2025.md)).

| 2025 headline | Value | Identity range |
|---|---|---|
| Unique participants | 2,837 (+11.1% on 2024) | 2,828 to 2,844 (0.6% of the estimate) |
| Retention (returning / prior-year participants) | 69.9% (+1.4 points) | |
| Girls' share of youth participation | 45.3% (42.4% in 2021) | |
| International participants (attributed, outside the US) | 1,086 | 1,079 to 1,086 |

Data trust is reported beside those numbers, not in an appendix: 98.9% of participants resolved with high confidence, 101 open review items,
2.2% of registrations failing counting-affecting DQ rules, 3 of 5 known sources onboarded. (Window: 2021 to 2025; 2021 is the left-censored year.)

```bash
make phase3                  # phase2, then facts + marts, shares + the policy check, every test, the executive report
make measure                 # seeds, load published snapshots, dbt run facts measurement
make shares                  # dbt run shares, then scripts/check_share_policy.py
make report [YEAR=2025]      # render docs/reports/participation_report_<year>.md (formatting only)
make publish YEAR=2025       # run EVERY test, then write an immutable snapshot to published/; refuses if any test fails
make docs                    # regenerate the data dictionary, docs/metrics.md and docs/access_policy.md
```

**Honest notes**
- **The identity range covers identity only.** It is tight (0.6%) because it spans only the uncertainty the pipeline knows about (about 100
  open review items, 13 flagged clusters). The synthetic truth falls inside it in every year, but 5 of 40 year-by-country cells fall outside, caused by
  look-alike merges the pipeline does not flag. Do not read the range as a confidence interval for "how many people play flag football".
- **The analyst share is pseudonymized, not anonymous.** 80% of its rows are unique on birth year, postal prefix, sex, country and year.
  A visible warning in the build says so (ADR-006).
- **Small-cell suppression is simplified** (primary plus secondary) and deliberately does not suppress a zero; ADR-006 explains why and
  names the production alternatives.
- **Annual REACTIVATED is almost 0** (1 person in 2023 and 1 in 2025) because churn in the generator is permanent; reactivation shows mainly in the US spring / fall view (about 100 a term).
- **The 2025 snapshot was taken with an uncommitted working tree** and records `git_dirty = true`; a clean-commit snapshot can be
  published at any time and becomes the latest. The 2023 to 2025 snapshots were taken on the original three-year window and are
  superseded by the five-year data (see the second example in `docs/reports/restatement_demo.md`).
- A generator amendment (some movers play in two countries in the move year) was made so country counting is actually exercised; it shifted
  every Phase 2 number slightly (ADR-003).
